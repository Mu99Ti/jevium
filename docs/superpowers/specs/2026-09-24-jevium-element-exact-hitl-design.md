# Jevium Element-Exact HITL and Resume Design

**Date:** 2026-09-24

**Status:** Approved by the user's "go ahead by your recommendations" instruction

**Supersedes:** runtime behavior claims in `2026-09-23-jevium-hitl-readme-design.md`

## Goal

Make human pauses element-exact, let configured credentials complete ordinary login and payment-detail entry automatically, and make the resume interaction clearly acknowledge the human step before the run continues.

## Requirements

1. Pause at the exact barrier that needs a person: CAPTCHA, OTP/2FA, a required secret field with no configured value, or the selected payment click.
2. When username/password are configured and no CAPTCHA blocks the page, log in without a human pause.
3. When card details are configured, fill observed card fields automatically; still pause at the final payment click.
4. While the human completes a step, show a clear done/resume interaction, acknowledge that the step was marked done, re-check the page, and continue.
5. Never send configured secret values to a model, store them in history, or print them.

## Recommended approach

Keep Jev choosing ordinary operations and observed targets. Add an executor-owned `TYPE_SECRET` operation for fields whose value comes from configured environment variables, plus deterministic pre-model fallbacks for:

- filling the first empty configured secret field;
- clicking a detected login submit after the login fields are filled.

Rejected alternatives:

- Unstructured credentials in `--task`: task text would leave the process through planner/model calls and be logged. Only the structured pair form is accepted, and it is stripped from the goal before any model call.
- Prompt-only auto-login: relies on the model choosing correctly every time.
- Code-owned selectors or site-specific login plans: forbidden by the repository contract.

## Configuration

Credentials are read from the process environment, normally supplied through git-ignored `.env`:

| Env var | Secret kind | Behavior when set |
|---|---|---|
| `JEVIUM_USERNAME` | `username` | Fills an empty observed login username field. |
| `JEVIUM_PASSWORD` | `password` | Fills an empty observed current-password field. |
| `JEVIUM_CARD_NUMBER` | `card_number` | Fills an empty observed card-number field. |
| `JEVIUM_CARD_EXPIRY` | `card_expiry` | Fills an empty observed expiry field. |
| `JEVIUM_CARD_CVV` | `card_cvv` | Fills an empty observed security-code field. |
| `JEVIUM_CARD_NAME` | `card_name` | Fills an empty observed cardholder-name field. |

No CLI credential flags. Secrets normally come from the environment; the only task-text form accepted is the structured `username <user> password <pass>` pair (plus labelled/password-first variants), extracted before planning, with the password removed from the goal and both values injected into the process environment for the run. Extraction requires a login intent and a password-shaped value (at least6 characters containing a digit and a symbol); anything else embedded in the task is still rejected before any model call. Tests never use real credentials.

## Snapshot contract

`jevium_core/snapshot.js` observes sensitive fields without exposing their values:

- Password inputs with `autocomplete=new-password` stay excluded.
- Other password inputs, login username fields, and detected card fields become fill actions with `secret` and `risk` metadata.
- Secret field values are reported only as `""` or `"***"` so the model can tell empty from filled without seeing contents.
- Guard state masks secret values; page-key state excludes them, so neither can leak field contents.
- A form containing a current-password field is marked as a login form for submit detection.
- Card-detection patterns run before the OTP pattern so a card security code is not misclassified as OTP.

## Decision contract

`jevium_core/model.py`:

- `TYPE_TEXT` continues to invoke the text LLM for ordinary fields.
- `TYPE_SECRET` is offered only for an empty field whose matching environment value is configured. Its value is never generated by a model.
- A required secret that is not configured remains an observable `TYPE_TEXT` fill when the field is empty so the model can select it, but the `secret` gate pauses before execution; `act` re-checks the configuration so a one-shot gate override cannot type a model-generated secret. A filled secret field offers no fill operation at all.
- Before any network call, `choose()` returns:
  1. the existing loading `WAIT` decision when applicable;
  2. a `configured-fallback` `TYPE_SECRET` decision for the first empty configured secret, ordered username → password → card fields;
  3. a `login-fallback` `CLICK` decision for a detected login submit only when the password is filled and no empty text/email input remains in that login form, unless the agent has already auto-submitted that exact page fingerprint.
- Page/model instructions list configured secret kinds, never values, and say ordinary configured login/payment-detail entry is not `NEEDS_HUMAN`.

## Gate contract

Gate order becomes element/barrier first, speculative/safety last:

| Order | Trigger | Condition | Human reason |
|---|---|---|---|
| 1 | `captcha` | `page_risks` contains `captcha` | Complete the CAPTCHA in the browser. |
| 2 | `pay` | selected target risk is `pay` | Confirm/authorize the payment click. |
| 3 | `otp` | selected target risk is `otp` | Enter the one-time code. |
| 4 | `secret` | selected fill is a required secret with no configured value | Enter the value manually or configure it in `.env`. |
| 5 | `model` | Jev chose `NEEDS_HUMAN` | Model-requested human barrier. |
| 6 | `page` | speculative `human_intervention` > 0.5 | Page state suggests a person is required. |
| 7 | `confidence` | confidence below `JEVIUM_MIN_CONFIDENCE` | Safety pause. |

Every `waiting_human` state carries `element: {label, risk, operation, target}` when the pause came from an observed target, or a CAPTCHA label for the page-level CAPTCHA gate. Existing one-shot override semantics remain: a non-`model` gate is authorized once by an explicit resume on the same fingerprint; `model` never auto-overrides.

## Executor contract

`Agent.command("act")`:

- `TYPE_SECRET` reads the matching environment value and types it directly.
- `TYPE_SECRET` never calls `field_text`, `pending_text`, or any model.
- History records `text="***"` and `text_helper="environment"`; `steps.jsonl`, TUI, demo state, and verifier therefore never receive the real value.
- A required secret fill without a configured value is gated before execution and re-checked in `act`.
- After a `login-fallback` click, the agent records the pre-click fingerprint and will not auto-submit that same fingerprint again.

## Resume UX

### TUI

- Banner reason includes the exact element label when known.
- Button label becomes **Done — resume**.
- On press, keep the banner visible, disable the button, and show `Marked done — rechecking the page and continuing…` in the banner and active line; write the same acknowledgement to the activity log.
- The next running/done state hides the banner.
- If the page does not settle after resume, `Agent.run()` yields a fresh `waiting_human` state with reason `Page did not settle after resume. Check the browser, then try again.`; the TUI re-shows the banner and re-enables the button.

### Plain mode

- Prompt: `Complete this step in the browser, then press Enter to mark it done and continue...`
- After Enter, print a recheck acknowledgement to stderr.
- stdin EOF does not resume into a gated mutation; it exits 1 with `stdin closed while waiting for human; resume was not sent.`

## Security constraints

- Secret values exist only in process environment memory and the live browser fill.
- The CLI strips a structured credential pair from `--task` before planning and rejects any remaining configured password/card value with exit2; users should prefer `.env`, not the task string.
- No configured secret values in model request bodies, planner/verifier prompts, history, logs, recordings metadata, or error strings.
- No model-generated selectors or JavaScript.
- Payment clicks are never executed without a `waiting_human` pause and an explicit Done — resume on that page.
- OTP is never read or guessed.
- SSO/OAuth identity-provider pages remain human pauses.
- Do not commit `.env` or any captured credential.

## Testing

Offline tests must not call paid APIs:

1. Configured secret fill returns `configured-fallback` without a network call and types the environment value with redacted history.
2. Login submit returns `login-fallback` only once per fingerprint.
3. CAPTCHA gate pauses before a configured secret fill and labels the element.
4. Missing password/card configuration pauses at the exact field.
5. OTP and payment gates carry element labels.
6. Resume settle failure yields `waiting_human` with the new reason.
7. TUI Done — resume press shows recheck feedback; a running state hides the banner; a waiting state re-shows it.
8. Plain-mode stdin EOF exits 1 without calling `resume()`.
9. CLI rejects a `--task` containing a configured password/card value with exit 2 before planning.
10. Live Chromium fixture observes password/card fields with masked values and correct risks.
11. Existing repository checks pass: `uv run ruff check .`, `uv run pytest`, `node --check jevium_core/snapshot.js`, `node --check jevium_core/static/app.js`, `uv build`.

## Out of scope

- Reading OTPs from email/SMS.
- Automating SSO/OAuth or identity-provider pages.
- Parsing or accepting credentials from `--task` or CLI flags.
- Auto-clicking the final payment confirmation without human resume.
- Changing the browser backend, model provider, or action budget.
- Committing or pushing changes.

## Success criteria

- With both login secrets configured and no CAPTCHA, a login form is filled and submitted without a model call or human pause.
- With card secrets configured, card fields fill automatically and the run pauses at the payment click with that element labeled.
- CAPTCHA/OTP/missing-secret/payment pauses identify the exact barrier.
- The TUI acknowledges Done — resume and recovers visibly if the page does not settle.
- No configured secret value appears in any model payload, history entry, log line, or test fixture.
